## 1.2 The correction is real where R-601 asked for it — driven

```
receipt naming NO builder commit
  -> status PROVENANCE_INCOMPLETE_NO_BUILDER_COMMIT
  -> the_literal_was_NOT_judged: True     contradicts_the_code: None
```

`builder_commit_of` reads only `builder_commit` / `carrying_commit` / `producing_commit`,
from the top level or from `seam`; **`seam.commit` is not in that tuple**, and `check_seam`
returns before any comparison when none is found. `front_door_at` checks `seam.commit`
against **DE's** module, which is what it names. DA's own statement of the round-70 error —
*"a commit id names a specific object; using it to locate a different object returns
something true and tells you nothing"* — is the correct diagnosis and the code matches it.

## 1.3 **FINDING — it can still be judged against the working tree, and the refusal names a commit it did not read**

`builder_index_call` (174-198):

```python
if at_commit:
    r = subprocess.run(["git", "show", f"{at_commit}:live/pm_research/be_daybook_build.py"], …)
    if r.returncode == 0 and r.stdout:
        src, src_from = r.stdout, f"git {at_commit}"
if src is None:                                   # ← the fallback
    src, src_from = BUILDER_PATH.read_text(), "working tree"
```

**Driven, on a receipt whose builder commit does not resolve in this worktree:**

```
builder_index_call(at_commit='deadbeef…')  -> source = "working tree"

check_seam(receipt with builder_commit='deadbeef…', literal matching HEAD's call)
  -> REFUSED: "`seam.index` is a LITERAL that contradicts the call AT THE RECEIPT'S OWN
              BUILDER COMMIT deadbeefdeadbeef… The receipt says
              'build_tape_index(tape_path=…, day=…)' …"
```

**The comparison was against the working tree; the message says it was against that
commit.** `check_seam` never inspects `call["source"]`, so the verdict — `agrees`,
`contradicts_the_code`, and the refusal — is computed from HEAD's builder while the
sentence attributes it to the receipt's commit. **That is the same defect R-601 ruled on,
arriving through the other door:** not "another seat's commit", but "a commit this worktree
cannot resolve".

**The proof that this is a slip rather than a design choice is two functions above it.**
`front_door_at`, handed an unresolvable commit, returns
`{"checked": True, "resolves": False, "why": "…is not readable at deadbeef…"}` — **no
fallback, no verdict.** Same author, same file, same situation, opposite handling.

**And it is near-term, not hypothetical.** BE 59 emits a `.v2` receipt **carrying a builder
commit** (R-601). Seats' worktrees routinely lag origin — mine was two commits behind when
this round opened. A verification run before that commit is fetched takes the fallback, and
the outcome depends on whether HEAD's builder happens to still make the same call.

**One line closes it:** refuse (or report `PROVENANCE_INCOMPLETE`) when
`call["source"] != f"git {b_commit}"`. The datum is already computed and already in the
output; nothing reads it.

# 3. R-602 as a design question

## 3.1 Is this a choice after seeing? **NO — and the alternative is the one that breaks the user's stated requirement**

**What could have been seen, checked rather than assumed.** At 09:03Z, when the ruling was
made: **zero** artifacts match `de_gate1_day_run*` in `derived/` (checked again at 09:10:59Z
— still zero, the smoke still running). No day sign, no `D(E0)`, no `Z`, no `p_location`
exists anywhere for any of the six days. The race read is not open. DA's pre-read has run on
fixtures only. What DA 72 read was wall clocks from three build receipts, hourly file
counts, heartbeats and calendar arithmetic.

**The honest residual, which I will not pretend is empty.** Build cost is a function of data
VOLUME (fragment bytes, tape rows, reference slugs), and volume is not independent of the
market. So "the pipeline is slow" is, very weakly, a function of the days themselves. **But
it carries no direction**: nothing in 608.4/1,471.6/2,115.7 s orders `D(E0)` or its sign,
and the change made on the strength of it does not touch the day set, the statistic, the
null or the multiplicity. Selection bites when the choice among alternatives can depend on
outcomes; here the two alternatives differ only in **when** the same six pre-named days are
read.

**And the decisive point runs the other way.** The user's own review, before any of this
existed: *"A five-day positive outcome will be directional only; with multiplicity two,
**six unanimous days are required for Holm significance**."* That is a requirement on **G**,
not on a date. **A clock-only bar delivers five days and therefore violates it.** R-555 had
already ruled the waiting principle explicitly — *"if any of the three future days fails its
verdict the set is NOT extended by choosing another day — it waits for the next closed day
that qualifies, in calendar order, and G stays 6"* — and MEM's round-115 row names that
clause as the thing that "removes the last place a choice could have been made after
seeing".

**Where I would not overstate it:** R-555's waiting clause is written about a day **failing
its verdict**, not about the pipeline being too slow. R-602 extends the same principle to a
second cause. It is a small extension in the same direction, and it should be recorded as an
extension rather than as something the ruling already said verbatim. The right
characterisation is narrower and stronger than "a new ruling": **00:06Z was an estimate of
when six days would exist; DA 72 measured that estimate wrong by at least 1.1 h; replacing a
wrong estimate of a completion time with the completion condition itself is a repair** —
provided the completion condition cannot admit anything the day set does not already
contain. Which is §3.3's whole subject.

## 3.2 Does G = 6 under the predicate keep the §7 arithmetic? **Yes — exactly, and in both formulations**

Recomputed:

| G | DE/R-555 form: 2⁻ᴳ vs α/m = 0.025 | DA 69 form: m·2⁻ᴳ vs α = 0.05 |
|---|---|---|
| 5 | 0.031250 — **fails** | 0.062500 — **fails** |
| **6** | **0.015625 — clears** | **0.031250 — clears** |

The two seats state the bar differently and **they are the same inequality**
(2⁻ᴳ < α/m ⟺ m·2⁻ᴳ < α), so the G = 6 requirement is robust to which form a reader picks up.
R-602's "2⁻⁵ = 0.03125 fails Holm at m = 2" is correct.

**Two things a reader should carry with that.** G = 6 is the **minimum** G at which
unanimity clears — 0.015625 against 0.025 is not a margin, it is one day of slack in the
day count and **none** in unanimity: 5-of-6 gives a one-sided sign p of **0.109**, an order
of magnitude away. The design is all-or-nothing by construction, which is what makes the
sixth day worth waiting for and also what makes any leakage into the day set fatal.

## 3.3 What the predicate MUST refuse — eight, and two of them are live today

R-602's wording: *"the clock ≥ 2026-09-09T00:06Z AND all six ruled days' SEALED day receipts
exist, verified by digest at read time."* Existence-of-a-file is a weak predicate. What it
must additionally refuse:

1. **A day whose arms were all inadmissible — CHECKED, and it is live.** Nothing in the
   runner refuses a day in which every arm fails R4: `run_day` appends
   `DEGENERATE_ARM_DAY_REFUSED…` entries, seals them and emits, and the day-level `status`
   is the constant **`"DAY_RUN_SEALED"`** regardless (2385-2386; grep for a
   no-admissible-arm refusal returns nothing). **Six such receipts satisfy the bar as
   worded and contribute zero day signs** — G would be 6 in the predicate and 0 in the
   test. The fix is available and non-economic: each receipt's
   `per_day_sealed_artifacts[*].admissibility.admissible` is present in the SEALED artifact,
   so the predicate can require ≥ 1 admissible arm per day without opening anything.
2. **A day re-rolled after others have landed.** "Verified by digest **at read time**" pins
   nothing about history: a day can be re-run any number of times before the read and only
   the last version is hashed. The digest must be **recorded when the day lands** and
   compared at the read — otherwise "wait for the sixth receipt" quietly permits "re-run
   until the set is complete", which is the one way waiting turns into choosing. DA's
   pre-read already emits `receipt.sha256` per day; six pre-read artifacts would be the
   record, and they exist for a reason.
3. **A substituted day.** The six must be *the ruled six* read from the committed params,
   never "the six receipts present". A receipt for 09-09 must not fill a hole left by 09-08.
4. **A day that failed its ledger verdict.** R-555 conditions membership on
   `day_quality_pass ∧ era_pure ∧ counts_toward_race`. A sealed DE receipt is not a day
   verdict; the predicate must require both, or a day that failed quality is admitted by
   having been run.
5. **A receipt whose producing code cannot be located — live today.** REV 49 §0: the runner
   stamps `producing_code_sha256` at emit, and the 09-03 receipt will name bytes that did
   not run. If "the sealed receipt exists" is satisfied by an artifact that cannot be
   attributed, the predicate imports that gap into the read gate. R-603's in-band
   supersession is what makes day 1 admissible; the predicate should say so explicitly
   rather than inherit it.
6. **Satisfaction by artifacts alone.** The conjunction must keep the clock as a genuine
   conjunct — six receipts before 00:06Z must **not** open the read, or R5's purpose
   (nobody sees a day while another is being run) is served only by accident.
7. **Unbounded waiting.** A predicate with no horizon converts "wait" into "wait until it
   works". The horizon and its fallback (G = 5, directional only — the user's own words)
   must be declared **now**, with the date, before the data. Otherwise the stopping rule is
   itself an unrecorded degree of freedom.
8. **An absent field reading as the old bar — the two-sided hazard.** DA's
   `gate_is_open` reads **DE's** `read_not_before_utc` (deliberately: "rather than carrying
   a second copy of the date"). If DE 86 adds the receipts half as a new params field and
   DA keeps reading only the clock, **DA reports the gate open at 00:06Z while DE refuses**
   — two implementations of one bar, silently disagreeing, which is exactly what MEM round
   144 named for G one day ago. DA must **refuse a params file that lacks the new field**
   rather than fall back to clock-only. Rule 11, at the gate.

**On DE 86's rehearsal:** R-602 expects it to refuse on 0 of 6 receipts. That is a
one-directional control. It should also be driven on **6 of 6 synthetic receipts before the
clock** (must refuse — item 6) and on **6 of 6 after the clock** (must admit), or the
rehearsal proves only that the door can close.
