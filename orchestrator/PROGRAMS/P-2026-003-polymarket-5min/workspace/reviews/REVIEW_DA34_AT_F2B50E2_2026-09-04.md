# ITEM 3 — **yes, there is a third route, and it is not an error path at all**

The two routes fixed today are both *per-version* drops: a version that cannot be read, and a version that cannot be parsed. Both shorten the history by removing **some** versions, and both are caught now. The remaining route removes **all** of them, and it involves no error.

Driven — `assert_withdrawals_monotone` pointed at a repository where the file's path does not exist (a rename, a move, a wrong default):

```
live tree      status READ  n_commits_touching_file 5  n_prior_versions 5  monotone TRUE  vacuous False
path absent    status READ  n_commits_touching_file 0  n_prior_versions 0  monotone TRUE  vacuous TRUE
```

**`monotone: True` over zero versions.** `git log --follow -- <path>` returns nothing, the loop never executes, no violation can be found, and the guarantee reports itself satisfied. `vacuous: True` and the `why` — *"this pass compares nothing — read `n_prior_versions_with_registry`, not the boolean"* — are honest and are the mitigation; but **the boolean is still `True`**, and the canonical-write guard I checked at DA24 tests `_mono.get("monotone") is not True`. A vacuous pass satisfies it.

**This is the codomain predicate one level up, applied to the guarantee instead of to a parse.** `monotone: True` is reachable from *"compared five versions, all consistent"* and from *"compared nothing"* — the same value from a measurement and from an absence of measurement.

**A related route, named because it is not hypothetical here:** `--follow` walks **HEAD's ancestry only**. This programme routinely rebuilds held chains and leaves the old shas as provenance; a withdrawal recorded in a commit that was later rebased out of HEAD's ancestry is never enumerated. The register documents exactly that pattern for DA's own round-20 chain.

> **Clause, and it is the module's own existing idiom.** `monotone` must be **`None`** — not `True` — when `n_prior_versions_with_registry == 0`, exactly as `NO_REPOSITORY` already returns `monotone: None` with *"a canonical write must refuse on this, and does"*. Vacuous is not a pass. And record the path/rename assumption explicitly: if the file is ever moved, the guarantee must refuse until the path is re-declared, rather than pass over an empty walk.

**So the answer to the question put to DA: yes — and the third is worse than the first two, because it needs no error to occur.**
