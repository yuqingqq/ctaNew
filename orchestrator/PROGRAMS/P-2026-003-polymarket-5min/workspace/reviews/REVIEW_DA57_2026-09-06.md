## 1. Is the digest set complete? — **More complete than the question implies, with one boundary that is real and unstated**

**It is not hand-listed.** `how_derived.not_hand_listed: true`, and:

* **REFUSE tier (7)** = two fixed files (`da_midnight_verify.sh`,
  `da_deploy_guard.py`) **plus the transitive closure of MODULE-LEVEL imports** of
  the two entry modules (`da_forward_day_verify`, `da_blackout_mask`), restricted
  to `live/pm_research/*.py` — `da_blackout_mask.py`,
  `da_content_liveness_rule.py`, `da_forward_day_verify.py`,
  `da_race_withdrawals.py`, `pm_tape_density.py`.
* **REPORT tier (26)** = the rest of the closure **including function-local
  imports**. So a lazily-imported module is recorded, just not fatal.

**Of my three candidate gaps, two are already closed:**

* **The installed unit AND the timer are both pinned at REFUSE tier**, with
  precisely the right reason: *"the installed unit/timer is what systemd actually
  runs; an edit here repoints or reconfigures the night without touching the repo
  at all."*
* **The interpreter is pinned** at REPORT tier. I verified the digest myself:
  `sha256(/home/yuqing/pricer-sol/venv/bin/python3)` and
  `sha256(/usr/bin/python3.12)` are **the same file and both match the record** —
  so the pin is on the real binary, not a shim.

**FINDING — the third gap is open and unstated: the stdlib and site-packages.**
I checked: **no non-repo path appears in `files[]` at all.** The interpreter
*binary* is pinned; **every library it loads is not.** A change under
`/usr/lib/python3.12/` or in the venv's `site-packages` reaches 00:06Z with no
digest, no report and no journal line.

DA's stated trade for the interpreter — *"losing a night's verdict to a distro
python update is the wrong trade"* — extends naturally to the stdlib, and I would
not argue for pinning it. **The defect is that the record does not say so.** It
states the boundary for the binary and is silent about the libraries, so a reader
cannot tell whether they were considered and excluded or simply missed. One
sentence in `interpreter.why` closes it.

## 2. Can a change to a recorded file reach 00:06Z without a deploy? — **No, for the REFUSE tier, and the enforcement is better than a single check**

`da_midnight_verify.sh:152–203` uses **two instruments, deliberately not the same
one**:

1. `sha256sum -c` (coreutils) over a manifest of the REFUSE tier — **and the
   guard's own digest is in that manifest**, so *"the guard is verified by
   something that is not the guard before the guard is asked anything."*
2. then the guard itself, which adds the installed units, the REPORT tier, the
   interpreter and the git anchor.

**And the forgery window is closed explicitly.** A canonical run **REFUSES (rc 7)
if `DA_DEPLOY_RECORD` or `DA_DEPLOY_TREE` are set** — *"the overrides exist so the
falsifier can drive both directions on a fake tree; allowing them on the nightly
path would let a forged record certify anything, which is worse than having no
gate."* **That is the right instinct and it is the one most instruments in this
programme have lacked**: the test hook cannot be used on the production path.

**A REPORT-tier change does reach 00:06Z** and is reported rather than fatal —
by design, and correctly tiered.

**Two costs, both stated rather than papered over**, which I note because both are
the kind usually left implicit:

* a drift refusal **loses the night's verdict**, and DA verified that is
  affordable rather than assuming it: `days_needing_verdict`
  (`da_forward_day_verify.py:97`) derives the day list **from disk** and returns
  any day with no artifact or one written while it was open, so the next run
  recovers it with a late `as_of` and a catch-up reason.
* a drift refusal **writes nothing to the log** — *"a guard that writes before it
  refuses has already done the thing it refuses"* — so the only record is the
  journal. **The gap is named as a known cost.**

## 3. "Commit is provenance not a gate" — **the right trade, for a better reason than the one given**

DA justifies it by register churn: *"pinning the commit would refuse nearly every
night — the register is appended several times a day."* True, but that is the
weaker argument, because it makes the choice sound like a concession to
convenience.

**The stronger justification is that the digests already gate what the unit
executes.** The commit adds nothing the seven REFUSE digests do not already cover;
it identifies *which history* those bytes came from, which is provenance by
definition. **Pinning it would refuse on a fact that has no bearing on what runs.**

**The residual window, and it is narrow:** the deploy act refuses a dirty, ahead
or behind tree (I drove all three), so `deployed_commit` was on `origin` at deploy
time. Its only failure mode is a **later history rewrite orphaning it** — the same
dangling-pointer class as BE's round-43 declaration pointer. Non-fatal, unfixable
from the run side, and worth one line in the record as a known limitation.

**The non-fatal git anchor does not open a run-time window** for the same reason:
what it anchors is already gated by digest.

## 4. Mutation audit v4 — the code-object digest is of the **MUTATED FUNCTIONS**, not the loader only

`da_population_mutation_audit.py:107–119`: the probe walks `vars(mod)`, takes
`__code__` where `__module__ == name` — **the module's own functions, not its
imports** — `marshal.dumps` each one, **and walks class methods too**, counting
them in `n_code_objects`.

So there are **two independent digests**, and the artifact carries both per mutant:

```
loader_code_sha256_moved     : true      <- the module object
functions_code_sha256_moved  : true      <- the module's own function code objects
cache_existed_before_import  : false
loader_source_matches_disk   : true
reached_the_interpreter = ok and (loader_moved or functions_moved)
```

And the field says exactly what it adds: *"the disk digest says the mutant was on
disk. These say the interpreter produced DIFFERENT code objects for it — which a
stale .pyc would make false while the disk digest stayed true."* **That is my B-1
finding, closed at the mechanism rather than at the sentence.**

## 5. The planted-stale-pycache known-bad — **driven, and it REFUSES**

Driven under the wrapper, `--selftest`, `0 failure(s)`:

```

                    and the probe sees it

                    cached bytecode still validates -- "the precise shape the reviewer

v3's PREDICATE    : the disk digest says the mutant is there and the loader's SOURCE

                    RAN.  REFUSAL, not green.
POSITIVE CONTROL  : with the cache DELETED the identical mutation DOES reach the
```

**Six properties, and three of them are stronger than what I asked for**: the

used there is `UNCHECKED_HASH`, which defeats the module's own `rmtree` and so
tests the guard rather than the housekeeping; and the anti-vacuity check makes the
control provably able to fire. **This is the most complete closure of any finding
I have filed.**
