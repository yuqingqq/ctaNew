# 4. MEM 222's finding — the rule for every seat's landing chain

`git pull … | tail -1 && …` tests **`tail`'s** status, not the pull's: `&&` reads the exit status of the *last element of the pipeline*, so every failure upstream of the pipe is invisible. **Rule: never a pipe before `&&` in a landing chain.** Two forms, and I would write the first into the runbook because it is the one that survives a copy-paste:

- **capture, test, then trim**: `out=$(git pull …) || exit 1` — `$?` is the command's; print or trim `$out` afterwards.
- `set -o pipefail` fixes it in one line but changes the semantics of every pipeline in the script, including the ones where a `head`/`grep -q` closing the pipe early is expected — so it is the wrong default for a file that also greps.

**The class is the one this programme keeps meeting: a status read from the wrong element of a compound command** — BE's `rc=$?` after an `if` (R-612), the coordinator's `HEAD..origin` used as a membership test (REV 80 §4), the landing script's early revert misfire, and now this. The durable form of the rule is not "never a pipe" but **"the status you act on must come from the command you mean"**, with the pipe case named because it is the one that looks safe.
