# 1. DE 102(2) (`ac9f590`) — design v23 and the scoped extension

## 1.1 The scoping works on DE's side, and its SELECTOR has three holes

`economic_fields_in_force(v)` filters `ECONOMIC_FIELDS` by `SEALED_FROM_DESIGN_VERSION` (the eight at 1, the three at 23) — driven: **v22 → 8 names, v23 → 11**, and the 09-03 receipt resolves to **v22/8**. The mechanism is right and the comment carries the reasoning. The selector that chooses the version is where the weight now sits, and it reads:

1. `provenance.design.path`, version parsed from the filename; else
2. the first `_design_v(\d+)\.json` in `split_residency_proof.tape_artifacts_opened`; else
3. **default 22**.

**Attack (a) — the default is the PERMISSIVE list.** Driven: a receipt with **no provenance at all** → `design_version 22`, three names not sealed. Any future receipt that fails to emit its provenance block — a partial write, a hand-made file, a bug — is judged under the *laxer* scope. That is absence selecting the weaker rule, in the scoping built to protect the seal. **The safe default is the STRICTEST list in force**; a genuinely old receipt is recognised positively (its `protocol`, its emit stamp), never by the absence of a field.

**Attack (b) — the selector reads the PATH and ignores the DIGEST beside it.** Driven: a receipt whose `provenance.design` carries a v22 *path* and any other *sha256* → judged **v22**. `provenance.design` is a `{path, sha256}` pair — the programme's own link shape — and only half of it decides. A receipt can therefore name a scope it was not produced under, and nothing compares the named digest to the design that was loaded. **Resolve the version from the pair: the digest must match the file the path names, or the version is UNKNOWN and the strictest list applies.**

**Attack (c) — the second fallback is order-dependent.** It takes the *first* `_design_v<N>.json` in an opened-paths list; the 09-03 run opened both a stale `design_v10__…json` and `design_v21.json`. For that receipt the fallback is never reached (there is no provenance block and no design in `tape_artifacts_opened`, so it falls to the default), but as a rule "the first design artifact a run happened to open" is not provenance at all. **Drop it, or make it refuse when the opened set contains more than one design version.**

## 2.2 The dataflow gate — right on the shapes that exist, **two escape**

# 3. R-660..R-662 — the coordinator class

## 3.1 The chained commit is **necessary and not sufficient** — three things driven in a scratch repo

1. **A directory pathspec sweeps another seat's file.** `git add -f -- w/ && git commit -- w/` with two dirty files committed **both**: `w/mine.md | 1 +`, `w/theirs.md | 1 +`. A file pathspec committed only its own. So the rule is not "commit by pathspec" but **"commit by FILE pathspec, never a directory or a glob"**.
2. **The TOCTOU window is real and it is the exact shape of R-661.** Check first (`git status --short -- w/mine.md` → 1 line, the coordinator's own edit), then a seat appends, then `add`+`commit` — and the commit carries **`+COORD` and `+SEAT-ROW`**. The chained form (`insert && add && commit`) closes R-662(C)'s case — a hold that did not hold — and leaves this one open, because the check precedes the insertion and the commit follows it.
3. **What closes it is a POST-condition, not a pre-check.** After committing, assert the commit's own diff for that path is exactly the bytes inserted (added-line count and content). No race can defeat a check made after the fact, and the remedy — revert and re-land — is available and already the programme's rule (never rewrite history).

**What else in the coordinator's landing can commit another seat's bytes:** any pathspec that is a directory or a glob (1); any commit naming **more than one path**, since the clean-check is written for the register alone and the second path gets none (the runbook change and the register in one commit is exactly that shape); and `git add -A`/`-u`, which the shared-tree prohibitions already forbid. **Recommend: the register procedure asserts cleanliness for EVERY path in the pathspec, and the post-condition in (3).**
