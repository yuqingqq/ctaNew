# ITEM 1 — the wiring control

## The substantive control FIRES. Its own falsifier does NOT.

The check that matters is `ok("matched_volume(" in inspect.getsource(compute), …)`. I drove it:

```
occurrences of 'matched_volume(' in compute(): 1   (L34: mv = matched_volume(rows, cs, isc, …))
shipped predicate on the REAL source     : True
shipped predicate with the call REMOVED  : False
=> the wiring predicate FIRES on an unwired source: TRUE
```

**So the control whose absence let a defined-but-uncalled primary reach a headline can fail.** That is the question asked and the answer is good.

### BE31-R1 — MEDIUM — but the module's own "WIRING KNOWN-BAD" cannot fire, and the predicate is a substring test

The known-bad is:

```python
_bad = src.replace("mv = matched_volume(", "mv = None  # unwired\n        _ = (")
ok("matched_volume(" not in _bad.split("mv = None")[0].rsplit("\n", 3)[-1], …)
```

Evaluated on both sources:

```
the module's own known-bad expression on the REAL source   : True
the module's own known-bad expression on the MUTATED source: True
=> it DISCRIMINATES: False
```

It returns True whatever the source says, because it inspects the last three lines *before* the marker it just inserted rather than re-evaluating the predicate. Its label claims *"with the call removed the predicate above can fail — it is not a check that passes on any source"*, which is exactly what it does not establish. **A control that cannot fail, guarding the class it was written for.** (The real predicate does fire — I showed that above — so the guarantee exists; it is the proof of the guarantee that is missing.)

Second, the predicate is a **substring test on source text**, and `compute()` already contains `matched_volume` in a comment at L29. Driven:

```
source with the call replaced by a COMMENT mentioning "matched_volume(" -> predicate says WIRED
```

So the control is one comment away from being satisfiable with no call — *"grep hits on vocabulary are not references"* (CLAUDE.md rule 16), in the control built to stop a defined-but-uncalled primary.

> **Clause.** Replace the substring test with an AST check that a `Call` whose func resolves to `matched_volume` occurs inside `compute` (and count bare `Name` references too, per the BE21 blind spot). Replace the known-bad with one that re-evaluates that predicate on a mutated source and asserts it goes False.

# ITEM 2 — `be_fill_ledger`. **The dollar outputs must NOT be published.** Two findings, both HIGH.

The fixture is as described — one action, three rows, 10/20/30 shares, first-row selection sees 10 — and the module does aggregate every row. But two things break the result.

### BE31-R3 — HIGH — on the only feed I may read, the ledger returns a confident **zero** where it should refuse

The 08-29 feed **predates** the scale fields: they were added at BE round 28 (`be_forward_metric.py:622-624`). Its rows carry `['any_fill_ahead','gen','score','score_incumbent','side','slug','t0','t_start','value_cents']` — **no `preventable_shares`, no `level`**. Run on it:

```
btc: n_rows 537,881  n_actions 299,386  rows_with_fill 80,929  rows_no_level 80,929
     shares 0.0   preventable_notional_dollars $0.00   gross_markout_dollars $617.95
eth: rows_with_fill 11,348  rows_no_level 11,348
     shares 0.0   preventable_notional_dollars $0.00   gross_markout_dollars $21.27
```

**`rows_no_level == rows_with_fill` on both coins.** The ledger *computed* the counter that says every filled row lacked a level, did not consult it, and emitted `$0.00` beside a non-zero markout. It refuses an empty **file** (R-141) and not an empty **field** — the empty-set trap one level in, and precisely the standing-instruction class: *a plausible number from a path that did not really run.* A reader takes `$0.00 notional` for a measurement.

> **Clause.** Refuse by name when `rows_no_level > 0` or when `shares == 0` while `rows_with_fill > 0`: *"this feed carries no `preventable_shares`/`level`; a scale cannot be formed from it."* The counter already exists; it needs a consumer.

### BE31-R4 — HIGH — "every row exactly once" is not "every fill exactly once", and the fixture enshrines the over-count

The audit's step 4 asked for *"an action-native fill ledger that aggregates **every fill exactly once**"*. The module's contract field says `"aggregation": "EVERY ROW OF EVERY ACTION, exactly once"`. Those are different quantities, because rows within an action **overlap**. Measured on the real feed and published yesterday as the justification for the ranking result:

```
rows/action 1.797 | 26.9% of actions have >1 row
consecutive-row spacing within an action: median 0.170 s
pairs closer than the 1.0 s FILL_HORIZON_S: 217,267 of 238,495  (91.1%)
```

A row's `preventable_shares` already sums every tranche in *its own* 1 s horizon. Summing sibling rows adds the same tranches again. So the ledger replaces prof.py's **under**-count with an **over**-count; neither is exactly-once.

**And the fixture encodes the over-count as the truth.** Its three rows sit at `t_start` **0.1, 0.2, 0.3** — 0.1 s apart, deep inside the 1 s horizon — and the fixture asserts the correct total is 60. On those timings the three rows describe largely the same tranches, so 60 is the double-counted figure, not the truth. **A falsifier that enshrines the defect as spec** — SEAT_PROTOCOL rule 16's fourth named instance, in the module built to repair an aggregation.

**And the feed cannot support the right answer.** Its fields carry no tranche or fill identity, so exactly-once aggregation is not computable from the feed at all; it needs tranche-level identity from `harmful_exposure_rows`.

> **Answer to the publication question: NO.** The dollar figures may not be published as they stand, and the blocker is not a caveat that can be attached — it is that the quantity is not the one claimed. Publishable after: (i) the empty-field refusal of BE31-R3; (ii) either de-duplication at tranche identity, or an explicit rename to something the number *is* (`sum_of_row_preventable_shares_WITH_OVERLAP`) carrying the 91.1 % figure; and (iii) the fixture's `t_start`s spaced **beyond** the horizon so its 60 is a genuine sum of distinct tranches. `POPULATION_NOTE` and `NOT_A_NET_RETURN` are otherwise accurate and unusually complete — the one-second horizon, the 50 ms cutoff, `stale_shares` held separately, and the gross/fees/exit/quote-size/inventory/capital disclaimers all check out against `harmful_exposure_rows.py:339-370`.

# ITEM 4 — one instrument, not two: yes, and DA's verifier is the right host

The publication provenance check needs three answers about any published number: **name the producer**, **census its committed call and reference sites (≥1 reachable from an entry point)**, **check the producing path is inside the repo**.

`da_arm_replay_verify` already owns all three capabilities: it parses another module's source with `ast` without importing it, it refuses by name when the source is missing or the shape is wrong, and `stub_or_real()` exists to distinguish a real path from a stub. Adding `provenance(artifact_path)` — read the artifact's `produced_by` / `producing_code`, census that symbol's call **and reference** sites across `live/pm_research/`, and refuse a path under `/tmp/**/scratchpad` or rooted in `~/ctaNew-wt-*` — is on the order of forty lines in a module whose refusal discipline is already correct, and the input already exists because BE's `emit()` writes `produced_by`.

Run against today's artifacts it would have returned `matched_volume: 0 committed call sites` yesterday and `be_read_cells.emit` today. **One instrument.**
