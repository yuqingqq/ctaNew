# ITEM 1 — DE's denominators: **present, and right**

DA's warning is the correct one to test — a wrong denominator reads as rigour — so I checked the arithmetic rather than the presence.

The denominator is `win["ADMITTED"]`, and it is right **by construction**, which is stronger than right on today's data:

```
win["ADMITTED"] += 1                    <- incremented immediately before
for k in GATE_KEYS:                     <- ONE loop, over EVERY gate,
    if not g[k]: gate_fail[k].append(slug)     once per admitted slug
```

Verified structurally: `gate_fail[k].append(slug)` occurs exactly once in the module, and `ADMITTED` is incremented before that loop. Therefore for every gate `k`, `len(gate_fail[k]) ≤ ADMITTED`, `n_passing_windows = ADMITTED − len(gate_fail[k]) ≥ 0`, and `n_failing + n_passing == n_evaluated` identically. **No gate is evaluated on a subset**: all gates are read off the same `g` dict for the same slug, so they cannot silently share a denominator they did not earn — which is the specific way a present-but-wrong denominator usually arises.

`all_gates_pass` is likewise gated: `None if ADMITTED == 0`, with the comment naming the real hazard — *"`all` over an empty evaluation is True in Python and that is exactly the wrong answer here."* Correct.

**One observation, not a finding.** The `None if win["ADMITTED"] == 0` branches are **unreachable**: `run()` raises `VacuousBattery` on `ADMITTED == 0` at char 52969, before the report is built at 54736. So the live guard is the raise; the `None` is defence in depth. Worth knowing, because a reader could believe the `None` is what protects them, and if the raise were ever relaxed the `None` would become load-bearing without anyone re-testing it.

### DA32-R1 — HIGH — `_hash_score_matches` returns `False` on a row it could not evaluate, and `False` means "this output is real"

`da_arm_replay_verify.py:212-213`:

```python
    except Exception:
        return False
```

This is the **stub detector**. `True` = "this score is the deterministic hash a stub emits"; `False` = "this score is genuine". Driven four ways:

```
a real stub score            -> True    (detected as a stub)
a genuine non-stub score     -> False   (judged REAL)
missing 'slug'               -> False   <-- same answer as "judged REAL"
non-numeric score            -> False   <-- same answer
gen not an int               -> False   <-- same answer
not a mapping                -> False   <-- same answer
```

**A malformed row makes the stub detector report that the output is real.** That is phantom failure inverted into phantom *success*, in the direction that admits a stub, inside the instrument written to stop exactly that — and DE is about to re-run the arms with real heads, which is precisely when this verifier is load-bearing.

> **Clause.** Return a third value (`None`/`UNEVALUABLE`) and have the caller count it as its own status, or raise. The two answers "I could not evaluate this row" and "this row is genuine" must not share a symbol.

**So: the sweep was not complete.** It is a good sweep of the shape DA had in hand; it did not scan for the shape structurally, and the one instance it missed is in the sweeping instrument itself.

# ITEM 3 — the class question. **Yes, for these two shapes, there is one predicate — and it does not cover the other family**

## The predicate

Both named shapes are the same defect:

> **The error/absence path returns a value inside the codomain of the measurement.**

Once that is true, the consumer cannot separate *"not measured"* from *"measured, and it came out this way"* — and **which named shape you get depends only on which in-domain value you happen to land on**:

| landing value | what the consumer reads | the name we gave it |
|---|---|---|
| the value that reads as success — `0` masked, `True`, an empty exclusion set | absence as a **pass** | R-411's shape, `n_masked 0`, `rows_no_level` unconsulted |
| the value that reads as failure — `0` bytes = dark, `False` = not identical, `False` = not a stub | absence as a **failure** | PHANTOM FAILURE |

They are not two shapes. They are one shape seen from two consumers.

**The predicate, stated so it can be run:** for each function, is the set of values reachable on an exception/absence path **disjoint** from the set reachable on a measured path? If not disjoint, it is a defect — whichever direction the overlap falls in.

**And the fix is the same in both directions**, which is why the unification is worth something: leave the codomain. Raise, or return a sentinel of a type the consumer must branch on. That is exactly why the many `return None` sites above are *correct* — `None` is outside the codomain of a bool, a sha, a registry dict — and why `return 0` from a byte count and `return False` from a boolean test are *not*.

**It is mechanically checkable** in the decidable cases (numeric, boolean, empty-collection returns) — that is the scan I ran above, plus a codomain test to cut the false positives. Where the return is a rich dict it degrades to *"does the absence path return the same shape as success"*, which is weaker but still catches the common case. And it applies to code nobody has looked at, which is the property asked for.

## Where it stops, stated plainly

It covers four of today's instances — `counts_toward_race` with no reader, `uncompressed_size → 0`, `rows_no_level` computed and unconsulted, `_hash_score_matches → False` — with one addition: where an in-domain return is genuinely unavoidable, the codomain test is replaced by **"is the accompanying status field consulted?"**, which is the zero-consumer census we already own. Two checks, one family.

**It does not cover the other family**, and I would rather say so than stretch it: `sealed_shape_is_unusable` returning literal constants, a map asserting its own length, a control whose subject was the calendar, a p that agreed because both sides called the same function. None of those is an absence path at all — they are **controls that cannot fail**, and the only general test for that is mutation: change the thing the control is about and require the control to go red. We have been doing that by hand, one control at a time.

So the honest answer is: **one predicate for the absence family, a second for the control family, and they do not merge.** The absence predicate is cheap enough to run repo-wide today. The control predicate is mutation testing and is not cheap, but it can be narrowed to controls that guard a published number — which is a small set and is exactly where it has bitten.
