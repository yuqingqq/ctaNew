# 3. **THE FINDING — L367 is closed, with the instrument DE measured and rejected one round earlier**

The comparison is now growth, for fixture and real alike:

```python
self.baseline_gb = _rss_gb()            # at construction
peak  = _rss_gb()                       # ru_maxrss -- a HIGH-WATER
row["growth_gb"]     = peak - self.baseline_gb
row["within_budget"] = (b is None or row["growth_gb"] <= b)
```

The scope mismatch DA 77 flagged is gone. **But both terms are `ru_maxrss`**, and DE 89's own
comment — written a round earlier, after measuring it — says why that fails:

> *"Measuring it on `ru_maxrss` reproduced the defect one level down: after an earlier run in
> the SAME process had pushed the high-water to its maximum, a later run's high-water did not
> rise at all, so its growth read ZERO and the budget could never fire. A budget measured with
> an instrument that cannot fall is a budget that only works once per process."*

**Driven on BE's own `_Stages`, twice in one process:**

```
A. fresh baseline (0.02 GB): 300 MB of work against a 0.001 GB budget
     -> REFUSED "this run GREW 0.293 GB from its own 0.02 GB baseline"      the control FIRES
B. a SECOND _Stages in the SAME process (ru_maxrss already 0.313 GB):
     150 MB of work against a 0.001 GB budget
     -> baseline 0.313, peak 0.313, growth 0.000, within_budget TRUE        ** it CANNOT fire **
```

**Production is safe today** — one build per process, and BE's own docstring says the baseline
is 0.1–0.2 GB there. **BE's battery is not**, and BE's battery already knows:

```python
_sb = _Stages({"S": 0.001}, cap_gb=CAP_GB); _sb.baseline_gb = 0.0
_sc = _Stages({"S": 99.0},  cap_gb=0.001);  _sc.baseline_gb = 0.0
```

**The known-bads hand-set the baseline to 0 after construction.** With the constructor's own
baseline — the process's already-raised high-water, by the time the battery reaches line 1330 —
they would read 0 growth and pass. So the controls test **the arithmetic, not the instrument**,
and the instrument's one failure mode is exactly what the hand-set hides. *(Line 1317 also
derives a budget from `_now_hw / 2` — an ambient-derived budget, the class DA 81 is generalising.)*

**The repair is DE's:** measure growth on **current** RSS (which falls), or take the baseline
from `_rss_now_gb()`. `_rss_now_gb()` already exists in this module, with a docstring
explaining precisely why a falling number was needed.

# 6. **(7) The `.v2`'s RECONSTRUCTION — honest, and one field short of safe**

The link is a proper pair — `supersedes.{path, sha256}` with `sha256 = 1f15d54f…`, and **v1 on

On the honesty question, the block is thorough:

```
producing_code.reconstructed_after_the_fact        = True
producing_code.run_head_recoverable_from_the_receipt = False
producing_code.NOT_an_import_time_capture          = "…read from the landing record, which is
                                                      weaker and must not be read as a stamp"
producing_code.run_head_source                     = "SUPPLIED ON THE COMMAND LINE from the
                                                      seat's landing report"
producing_code.what_this_check_can_and_cannot_do   = "matching the blob at the named commit
                                                      CONFIRMS those bytes existed there; it
                                                      cannot prove the run used that commit"
producing_code.builder_commit                      = b827ca2e…   digest_matches_that_commit: True
```

**My answer: naming what it cannot know is the RIGHT call, and "NOT RECOVERABLE alone" would be
worse** — it would discard a fact that is true and useful: the bytes at `b827ca2e` **are** the
bytes that ran, digest-matched. Throwing that away to avoid over-claiming is the mirror error.

**But rule 13's own lesson applies: automated readers resolve receipt FIELDS, not sidecar
annotations.** A consumer keying on `producing_code.builder_commit` gets a commit that matches
the bytes and is **not** the run's head, and the five fields that say so are different keys. The
fix is not more prose — it is to put the disclosure **in the key**: `builder_commit_RECONSTRUCTED`
(so a resolver looking for `builder_commit` finds nothing), or a `status:
RECONSTRUCTED_NOT_A_STAMP` as the block's first field. **BE already uses that pattern twice in
this same receipt** — `receipt_corrected_from`, `commit_corrected_from` — where the correction
rides beside the value. Here it should ride *in the name*.
