## A.1 **FINDING — the citation is transcribed; the digest guards the file, not the transcription**

`BE_CANCEL_AXIS_NULL` (`de_phase4_diag_runner.py:1789–1818`) holds **hardcoded
literals** for every statistic — mean, sd, min, max, p05, p50, p95, decisions,
n_draws on both arms, plus a `population_block`. `load_cited_be_null()` opens
BE's artifact and **verifies its sha256, refusing on mismatch** (`:1837–1841`).
**But every number actually used comes from the literal dict** — `:1902–1912`,
`:1928–1929`, `:1935`, `:1950`, `:2128` — not from the file it just parsed.

**What the digest DOES protect, and it is the more important half:** if BE
re-emits, the digest breaks and the emission **refuses** rather than silently
following. DE says so explicitly (`be_v2_status_at_emission_time`), and that is
the right behaviour.

**What it cannot protect:** a transcription error made at copy time is invisible
to it forever — the file is unchanged, so the check passes while the number used
is wrong.

**So I did the check the code does not.** Parsing the literal by AST and
comparing against `be_cancel_axis_null_v1.json`:

> **21 transcribed values checked — mean, sd, min, max, p05, p50, p95, decisions
> and n_draws on both arms, plus all three population counts. MISMATCHES: 0.**

**The transcription is faithful today. The guard could not tell you if it were
not.** Cheap close: `load_cited_be_null` already parses the file — read the
per-arm values from the parsed JSON instead of the literals, and the citation
becomes a read.

*(Same shape at `BE_PUBLISHED_CASCADE_HEADLINE = {8.7013, 5.5684}` — hand-rounded
4-dp literals. The 1e-3 cross-check therefore compares a computed value against a
transcribed one; it is still a real check, and its tolerance is doing exactly the
work the rounding requires.)*

# (B) DA 55

## B.1 **THE DIRECT QUESTION — the digest proves the DISK, not the interpreter. But the PAIR closes it, and only one of the three measures does any work.**

`da_population_mutation_audit.py:202` is `executed = digest(t)` — taken after the
mutant is written and the cache removed, **before** the suites run. **That is a
digest of the file on disk. It does not observe what the interpreter executed.**
The field name `source_sha256_while_the_child_ran` asserts exactly one step more
than the field proves, and a reader taking it alone would over-read it.

**DA's own comment states the correct claim** (`:198–200`): *"…hash to the mutant
while the interpreter ran the original. Paired with the cache removal in
`run_suite`, the pair is checkable rather than asserted."* **The conjunction —
disk digest + no cache for the interpreter to read — does close the gap**, and
the conjunction is present: `rmtree` before the child (`:119`, `:201`),
`PYTHONDONTWRITEBYTECODE=1` in the env (`:120`), `-B` on the command line
(`:121`), `rmtree` again after restore (`:205`), and a restore-digest refusal
(`:206–208`).

**But I tested which measure is actually doing the work**, same fixture as A-6:

```
mutate 0.5 -> 0.0 (same byte length), mtime restored:
  python3 -B                            -> 0.5   STALE
  PYTHONDONTWRITEBYTECODE=1 python3 -B  -> 0.5   STALE
  after rm -rf __pycache__               -> 0.0   CORRECT
```

**`rmtree` is load-bearing. `-B` and the env var are belt against a *different*
failure — the flag being lost through the environment — and do nothing against a
cache that already exists.** DA's stated reason for `-B` ("so the flag cannot be
lost through the environment") is right about what it defends; it should not be
read as a second defence against staleness.

**The hazard is closed. It is closed by exactly one of the three measures**, and
the field that certifies it should either be renamed
(`source_sha256_on_disk_before_the_child`) or carry the pair in its own value.
