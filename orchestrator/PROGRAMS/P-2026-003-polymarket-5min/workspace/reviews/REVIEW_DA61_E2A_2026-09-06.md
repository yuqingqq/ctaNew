## A.4 The four self-caught fixes, attacked

### A.4.1 The quantity-step estimator — **robust, and my first probe was wrong**

I first fed it `[0.25]×50 + [3.14159]` and got 2.89159, which looked like a defect.
**That was my error: two distinct values give exactly one diff, and the mode of one
value is that value.** The docstring's case is a tape *of 0.25 multiples*. Corrected
and re-driven:

```
pure 0.25 grid, 59 distinct values      -> 0.25
  + ONE off-grid 3.14159                -> 0.25     (v4's GCD fallback gave 1e-5)
  + TEN off-grid values                 -> 0.25
  a THIRD of the tape off-grid (30/89)  -> 0.25
```

**The fix is real and materially stronger than the GCD form**, which collapses to
the representation floor on a single off-grid value — the FIL 1e-6-vs-1e-4
mechanism, which is the same defect I filed as a record error in REVIEW_DA60 §1.
Refusing to touch the *price* tick because it is pinned by the E1-A control is the
right call: that number must not move.

**But the estimator has a sparsity boundary, and it is unmarked:**

```
ONE distinct quantity   -> returns that value      (n_distinct = 1)
TWO distinct quantities -> returns their DIFFERENCE (n_distinct = 2)
```

`order_qty = float(qty_step)` at `:383` — **this is not a diagnostic, it is the
order size the whole simulation places.** On a day with fewer than three distinct
trade quantities the returned number is not a step and nothing marks it as such.
Reachable on a thin symbol-day — **and v6 exists to admit thin symbol-days**, so
this boundary goes live exactly when v6 lands. A counted status
(`QTY_STEP_UNDERDETERMINED`, n_distinct < 3 → refuse the day) closes it.

## A.5 **THE SPLIT ORDERING FALSIFIER — the half DA kept is FALSE, and I constructed the case**

DA found *"ProbQueue ≤ RiskAverse per episode"* false on **cost** — favourable drift
makes a chase cheaper than a fill — and split it: **cost at aggregate, quantity per
episode, the latter as arithmetic.** The split's reasoning on cost is right. **The
quantity half is not arithmetic.**

**Why, from the code.** `simulate_episode`: ProbQueue fills with certainty only once
some trade arrives with `front = 0`, i.e. `v_before ≥ queue_ahead`. RiskAverse fills
`clip(total − queue_ahead, 0, q)`, which is positive as soon as the *total* exceeds
the queue. **Between those two conditions there is a regime where RiskAverse fills a
sliver and ProbQueue is still a coin flip.**

**Constructed and driven** — queue_ahead 100, order 10, one opposite trade of 105,
depth at L 200, 2,000 seeds:

```
MARGINAL (the queue cleared by the last trade's own volume)
   RiskAverse 5.0   ProbQueue 0.0   max prob 0.5
   ORDERING VIOLATIONS: 993 / 2000  =  49.6%

PARTIAL OVERSHOOT (two trades of 60; total 120 > qa 100, no trade with front = 0)
   ORDERING VIOLATIONS:  13 / 2000  =   0.65%

FULL OVERSHOOT (a trade arrives with v_before >= queue_ahead, so prob = 1)
   ORDERING VIOLATIONS:   0 / 2000
```

**The property holds exactly in the full-overshoot regime and nowhere else.** It is
an ordering of **expectations**, not of realisations.

**And the consequence is worse than a wrong comment**, because of what the runner
does with it:

> `if viol: vd = {"state": "REFUTES_THE_BRACKET", "why": "… That ordering is
> arithmetic per episode, so this is an implementation defect and no overlay
> verdict may be read."}`

**A correct model disagreement in the marginal regime would declare the instrument
broken and suppress the gate.** A self-falsifying instrument is a virtue — I said so
when I approved the design — but only if what it falsifies on is actually
impossible.

**Why ICP's `n_ordering_violations = 0` is not evidence the property holds.** ICP's
episodes carry `n_opposite_trades_p50 = 514.5` against `queue_ahead_p50 = 683.5`,
with fill rates 0.935 / 0.978. With 514 trades per episode the chance that no trade
arrives with the queue already cleared is small — **the ICP population sits far from
the marginal regime, so the control never entered the regime it is wrong in.**
Rule 16's shape: a control that did not fire because its case was absent, on the one
symbol measured so far.

**What v6 must say instead:** the ordering is `E[filled_ProbQueue] ≥ filled_RiskAverse`.
Test it per episode **only where some trade has `front = 0`** (a computable
predicate), carry the marginal episodes as a **counted status**, and test the
expectation over the population. A per-episode realisation test on a stochastic
model is not a falsifier, it is a coin flip with a veto attached.
