# ITEM 2 — the ERA_AUTHORITY invariant

### DA22-R2 — MEDIUM — a value can still be used with no cite, and the field that discloses it is consumed by nothing

`_auth_checked = admissible_table is None or authority_table is not None` (`:1550`). Supply an `admissible_table` and no `authority_table` and the authority check is off. Driven:

```
day_era_admission("20260829", admissible_table={"clob_v3_1": True})
  -> race_admissible_by_era: True    era_authority_checked: False
```

DA's reasoning is sound as far as it goes — production passes no table, so production is always checked, and the three named harnesses are comparing malformedness. The gap is downstream: `grep -rn era_authority_checked` over `live/pm_research/` and `orchestrator/` returns **one producer line and three selftest lines**. No gate, no composition, no BE gate reads it. A verdict could be emitted carrying `era_authority_checked: False` and nothing would refuse it — a disclosure with no consumer, which is rule 17's shape one layer out.

> **AMEND clause.** Make the disclosure load-bearing where it matters: BE's gate 1 (or `split_verdict`) refuses a verdict whose `era_admission.era_authority_checked` is not True. One conjunct, and it converts a field nobody reads into the interlock it was written to be.

### DA22-R3 — MEDIUM — `clob_v5` is a contradictory pair, and the module's own doctrine says how to fix it

`ERA_ADMISSIBLE["clob_v5"] = True` with `ERA_AUTHORITY["clob_v5"] = None`. Driven: `era_authority_for("clob_v5")` REFUSES; the other three eras return their cites. So a day touching v5 raises `ValueError` inside `day_era_admission`.

Refusing is right in principle — an unruled era must not be quietly authoritative. But the module already has a cleaner expression of exactly that: *"An era absent from this table REFUSES. A new collector version is not admissible by default, and silence is not a ruling."* Keeping `True` in the value table while nulling the authority creates a pair that contradicts itself and refuses **later**, through a different message, than the mechanism designed for it.

Is a day that should pass broken? Only a v5 day, and none exists — so this is latent, not live. It stops being latent the night v5 deploys (`V5_DEPLOY_RUNBOOK_2026-08-31.md`, `HEARTBEAT_APP_V5` and `MODE_SPEC` all exist), and the failure mode is the nightly unit raising rather than refusing by name.

> **AMEND clause.** Remove `clob_v5` from `ERA_ADMISSIBLE` until it is ruled. The absent-entry refusal is the designed path, its message is the informative one, and `era_authority_audit` keeps reporting it under `eras_without_authority` either way.

### DA22-R4 — LOW-MEDIUM — the cite audit's coverage is partial and does not say so

`cited_entries` collects only `R-<n>`, so an era whose authority is a **dated USER ruling** is audited for nothing. Driven against origin's register:

`clob_v4_1` passes `era_authority_for` (the regex matches `USER RULING 2026-08-31`) and then appears in neither `eras_whose_cite_does_not_name_them` nor anything else. Half the table is silently unexamined while the output reads as a complete audit — absence reading as a pass.

**One property worth stating rather than filing:** the audit resolves cites against the register **in the tree it runs in**. At the held tip it reports `R-497 → resolve: False` — its own governing cite unresolved — because the held chain's `COORDINATION.md` (484 entries) predates R-497. Against origin's register (489 entries) it resolves and names the era. Not a defect; but the answer travels into an artifact, so it should carry the register's identity.

> **AMEND clause.** Emit `eras_not_audited` with the reason (`authority is a dated USER ruling, not a register entry`), and record the register's path **and sha256** beside `n_register_entries`.
