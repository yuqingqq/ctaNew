# 4. §A.6, answered precisely — so DA 80 tests the right thing

**DA's `_derived_dir` does not read `PM_DATA_ROOT` and does not use the shared resolver. It
cannot: the try-branch raises on every call.**

```python
def _derived_dir() -> Path:
    """… through the programme's ONE data-root resolver -- imported, never a second
    implementation of 'where is the ledger' (R-562/R-564)."""
    try:
        import de_data_root as BDR
        return Path(BDR.resolve()) / "data" / "pm_5min" / "derived"
    except Exception:
        return HERE.parents[1] / "data" / "pm_5min" / "derived"
```

Driven:

```
de_data_root.resolve() returns a dict
Path(<dict>) -> TypeError: argument should be a str or an os.PathLike object …
_derived_dir()                     -> /home/yuqing/ctaNew-wt-rev/data/pm_5min/derived
HERE.parents[1]/data/pm_5min/derived -> /home/yuqing/ctaNew-wt-rev/data/pm_5min/derived   identical
the shared resolver would have said -> /home/yuqing/ctaNew/data/pm_5min/derived
```

**The docstring is false of the code**: the import happens, the call happens, and its result is
discarded by an exception the bare `except Exception` swallows. Every read goes to the module's
own tree.

**What DA 80 must therefore test, and it is not what a resolver test usually tests:**

1. **That the try-branch returns a path at all** — i.e. `_derived_dir()` equals
   `Path(de_data_root.resolve()["data_root"]) / "pm_5min" / "derived"`. A test that only asks
   "is the answer right?" passes today from the shared tree.
2. **From a worktree**, because that is the only place the two branches differ. **Run only
   from `/home/yuqing/ctaNew` and the broken fallback gives the correct answer** — the bug is
   invisible exactly where a test is most likely to be run.
3. **With `PM_DATA_ROOT` set to a worktree path AND unset**, as dispatched — but knowing that
   for this module the variable changes nothing, so a pass under both settings proves the
   resolver is *insensitive*, not that it is *right*.
4. **A bare `except Exception` around a resolver call is the finding, not the `TypeError`.**
   Fixing the call without narrowing the except leaves the next resolver change silently
   falling back again.

**And there are three root rules in DA's own modules, not one:** this one (tree-relative via a
dead try), `da_accrual_report`'s `os.environ.get("PM_DATA_ROOT") or HERE.parents[1]`
(env-first), and `da_book_verify`'s own. DE's resolver, driven from a worktree with
`PM_DATA_ROOT` unset, returns the canonical ledger and `require_canonical` admits. **The hazard
is not the environment variable; it is four rules for one root, one of them broken in a way
that only shows up outside the shared tree.**
