# 1. The stop decision (R-659)

## 1.1 Was stopping a four-minute-old run the right instrument?

**Yes, and the reason is a distinction the register should carry, because it reconciles this ruling with R-603's opposite one.** At R-603 a run 13 minutes in would have emitted a receipt that **misnamed its producing code**, and the ruling was *do not touch it* — supersede the receipt in band. Here a run four minutes in would have emitted a receipt that **published three outcome counts**. The two rulings point in opposite directions and both are right, because:

> **A provenance error is correctable in band; a disclosure is not.** A `.v2` receipt can name the digest that really ran, and the v1 stays as provenance costing nothing. A `.v2` receipt cannot un-publish a number: rule 13 forbids editing the frozen artifact, so the counts would sit in the ledger for the life of the programme with a "nobody quotes them" beside them.

That asymmetry — not the size of the defect — is what makes stopping right here and wrong there. Against the alternative the coordinator names (let 09-04 land under v22, seal from 09-05, add a "nobody quotes" rule): the cost of stopping is **≈ 30 minutes of chain time against DA 79's ≈ 9.4 h of horizon margin**, and it buys the difference between one historical day with the counts open and two. The cheap option buys nothing durable and doubles the exposure. **AGREED with the ruling; the reasoning above is what I would add to it.**

One thing the stop does NOT cost, and it is worth stating because the 09-03 chain teaches the opposite intuition: **nothing was consumed.** The run wrote no artifact; the ruled day set is untouched (§1.2); this is the third artifact-free termination of the programme (REFUSED 09:50Z, KILLED 12:05Z, STOPPED 14:38Z) and the only one that was a decision rather than a defect.

# 2. DA 92 (`795b039`) — the marker rule

## 2.1 A marker is a **label**, not a guard — and that is decidable

The census admits a non-head literal on an IDENTIFIER word, a FUNCTION name, or an allowlist entry. **None of the three looks at what the literal is USED for.** Rename a stale pin `SUPERSEDED_X` — or move it inside a function whose name contains `falsif` — and it is `MARKED_ADMITTED` while still flowing into `open()`. So the answer to the coordinator's question is **no: a marker on a literal that flows into a file open is not a guard, it is a label on a live read.**

The composition with DA 93 is exact and I would state it as the rule: **a literal that flows into a file open must name the head — marker or not; the marker governs only literals that do NOT flow into an open** (prose, supersession chains, known-bads, fixtures). That makes the two instruments complementary instead of overlapping, and it means DA 93 must show, per row: the dataflow verdict (does it reach an open, directly or through one assignment), the marker verdict, and the composed status — with a falsifier for the case that matters most, **a marked literal that IS opened**, which today's census admits silently.

## 2.2 The word-level test, driven

| identifier | marks |
|---|---|
| `SUPERSEDED_PARAMS_REL` | `superseded` |
| `_bad_pin` | `bad` |
| `KNOWN_BAD_PATH` | `known_bad` |
| `falsifier_input` | `falsifier` |
| `badly_named_thing`, `_notbad` | **None** (word-level, not substring — correct) |
| **`supersededParams`** | **None** — camelCase is invisible to the `[_\W]+` split |
| **`BAD_REQUEST_PATH`** | **`bad`** — any identifier carrying the token `bad` is admitted |
| **`PREVIOUS_PARAMS_REL`, `old_params`** | **None** — the natural names for a deliberate historical pin do not mark |

Two edges in opposite directions: `bad` is broad enough to admit an unrelated identifier, and the honest names a seat would reach for (`OLD_`, `PREVIOUS_`) refuse a correct guard, which trains seats to rename rather than to think. **Recommend: drop the bare `bad` (keep `known_bad`), add `previous`/`prior`/`historical`, and require the marker to sit on the assignment the census reports — none of which matters once §2.1's dataflow rule lands, because then the marker only decorates literals nobody opens.**

## 2.3 The allowlist has no chain head — in the chain-head instrument

`_allowlist()` globs `*_nonhead_allowlist_v*.json` and merges **every version it finds**: `for f in sorted(...): out[(seat, names)] = {...}`. A v2 that **removes** an entry cannot remove it — v1 is still read and still allows it. The instrument built to refuse a reader that ignores supersession **reads its own declaration set without resolving a head.** Today the exposure is zero (no allowlist file exists), which is exactly why it should be fixed now: the first one written will be v1, and the second will be the defect. **Fix: resolve the allowlist family through the same head resolution the census applies to everything else — and refuse if it does not resolve to one.**

## 2.4 Is `_bad_pin`'s marking R-235-clean? Yes, with the caveat that applies to every self-report

DA reads an identifier NAME out of DE's source. That is not a statistic and not a re-implementation of DE's logic; it is one-way, it only ADMITS (it can never produce a result), and DE cannot make DA compute anything by naming a variable. **R-235-clean** — the same standing I gave `wrapper_measured` at REV 65 §2. The caveat is the one from §2.1: what DA reads is DE's *declaration of intent about its own literal*, so the census is not an independent check of the use, and it should say so in its own output (`marker` is a claim by the file's author, not a finding).
